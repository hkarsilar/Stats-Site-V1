# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**StatsCapybara** (statscapybara.com) — a free, interactive statistics course: 102 interactive lessons across 8 courses in two tracks — **The Statistics Core** (Stats 1–3 + ML & AI) and **The Research Toolkit** (Methods, Data, Writing, Ethics — all complete; see ROADMAP.md) — each a written explanation plus a hands-on canvas visualization, plus 21 tool pages (including 3 printable cheat-sheet posters) and 5 long-form guides (see **Long-form guides** and **Cheat-sheet posters** below). It is a **plain static multi-page site**: vanilla HTML/CSS/JS, **no build step, no framework, no npm dependencies, no bundler**. Hosted on GitHub Pages. (One generated asset: `assets/js/search-index.js` — see Full-text search below.)

## Where things live (important)

- **The working directory IS the git repo root** — the folder GitHub Desktop clones as **`Stats-Site-V1`** (remote: `https://github.com/hkarsilar/Stats-Site-V1`). Run `git` commands here directly (just `git <cmd>`, from the repo root). The site's pages, assets, and `CNAME` all sit at this root and are published from the `main` branch by the GitHub Actions workflow in `.github/workflows/pages.yml`, which ships the committed tree **minus the development files** (see the deploy note in Commands below). Every file it ships is copied byte-for-byte; nothing is processed, so the no-build law is untouched.

If the user pastes a "roadmap prompt PN", read both files first; when a session completes a prompt, tick its box in ROADMAP.md's status tracker **and push the work to `main` — see the "Finishing a session" rule in the Commands section below; it is not optional and it is not the user's job.**

## Commands

There are no tests, linters, or build tools. The workflow is: edit a file → syntax-check JS → preview in a browser → commit.

All commands run **from the repo root** (the `Stats-Site-V1` folder) and assume only **`node`** on your PATH — Node is the one runtime with the same command name on macOS, Windows and Linux, so preview and the health check need nothing else. **The two content generators are Python 3**; the command name differs by OS, so use whichever your machine has: **`python` on Windows, `python3` on macOS** (this Mac has no bare `python`). Both `tools/*.py` scripts also carry a `python3` shebang and the executable bit, so on macOS/Linux you can run them directly as `./tools/inject-faqs.py` with no interpreter prefix at all.

`.claude/launch.json` (committed in the repo, with repo-relative paths) defines the servers above (`site` and `subpath`, plus `site-alt` on 8098 as a fallback when another session holds 8097) via **`node tools/serve.js <port> [root]`**, so the preview tooling spawns identically on any clone — Mac, Windows or Linux — with no Python needed. `tools/serve.js` is a zero-dependency static server (Node built-ins only) that mirrors `python -m http.server`: it serves a directory's `index.html` and 301-redirects a slash-less directory request so lessons' `../../` links resolve exactly as on GitHub Pages.

**`node tools/audit.js` is the permanent health check and a required pre-commit gate** (zero-dependency, Node built-ins only; run from the repo root). It exits non-zero on any **error** and cross-checks the whole site against its single sources of truth: coverage per ready lesson (`CHECKS` 3×4, `faq_data.py` 3 Q&As, `QUIPS`, `SNIPPETS` warn-only, `SOFTWARE` info-only, `sitemap.xml`) with no stale/orphan keys; per-lesson HTML (one GA tag, canonical + `og:url` = true URL, `og:type` article, LearningResource + BreadcrumbList + FAQPage JSON-LD all parse, `data-course`/`data-section`, the `Section N.n` eyebrow vs `curriculum.js`, meta description present + 50–160 chars as a warning); root/tool pages (GA, canonical, description, OG; `404.html` GA only); all internal `href`/`src` links resolve on disk with no leading-slash paths, **and any `#fragment` they carry names a real `id` in the target file** (P39 run 4 — nothing else checked this, so a typo'd `problems.html#p2-99` silently dropped the reader at the top of the page; anchors that only exist after `site.js` runs are listed in **`JS_IDS`** in `tools/audit.js`, and that list should stay short); search-index freshness + slug coverage; and the homepage course/lesson counts vs `curriculum.js`. **Directory 404s (CHECK 3d–3e):** section hubs listed in `HUB_FOLDERS` get the full page contract, and **no folder that publishes pages may lack its own `index.html`** — the check that closes the class of 404 a link check structurally cannot see (see **Section hubs** below). **Structured data (P36, checks 7–8):** every JSON-LD object also passes a per-type required-fields check (name/url; `itemListElement` with well-formed ListItems for BreadcrumbList; `mainEntity` with `acceptedAnswer.text` for FAQPage); every tool page must carry a **BreadcrumbList** (Home → Statistics Toolbox → Tool) and `quiz.html` a **Quiz** block; the homepage's **Organization + WebSite (SearchAction) + ItemList-of-Courses** blocks are deep-checked against `curriculum.js` (course names, per-course lesson counts, track titles, first-lesson URLs, `educationalLevel`s); each lesson's LearningResource must name its own course in `isPartOf` and carry its course's expected `educationalLevel`. **Meta hygiene (P36):** no two audited pages may share a meta description (error), every `<title>` must follow `Thing — StatsCapybara` (the homepage is brand-first), and root-page descriptions get the same 50–160-char length warning as lessons. **APA statistic/p consistency (P39 run 12, CHECK 9):** the site publishes worked APA sentences in two places — every `software.js` entry's `apa` string and every `.apa-quote` blockquote baked into a lesson or guide — and nothing ever checked that the *p* matched the statistic printed beside it. One did not: `simple-linear-regression` reported `R² = .21, β = .45` against a `b`/`SE` that gives `t(48) = 4.05`, i.e. `R² = .25, β = .50`. CHECK 9 loads `viz.js` into the audit's existing bare sandbox (it needs no DOM shim) and recomputes *p* from each `t`/`F`/`χ²`/`z`/`r` with its df, erroring on a mismatch — the statcheck test `apa.html` already offers readers, turned on the site's own content. It is **deliberately conservative**: a statistic is paired with a *p* only when that *p* follows it directly, in the same clause and within 80 characters, because an APA sentence routinely continues "…, *p* = .011, ηp² = .08: … *F*(1, 76) = 15.2, *p* < .001" and a greedy pairing reports eight false mismatches on this corpus (verified). Anything it cannot parse confidently is skipped rather than guessed at, and it reports the pair count as info (27 today). **If it fires, fix the sentence, not the check.**

**Warnings/info never fail the build** — only errors do. Run it (and fix any errors) after every content change and before handing a diff back for review.

**Math (P66): `node tools/math-check.js` is the statistical regression gate — REQUIRED whenever `assets/js/viz.js` or any tool-page math changes.** `audit.js` checks the site's wiring exhaustively but not one line of its math, and the brand promise ("statistics must be correct") had no regression test until this. It loads `viz.js` into a `vm` context under a minimal `window`/`document` shim and runs **591 assertions**, each citing its published source and carrying a tolerance normally set to that source's rounding precision (a value quoted to 4 dp gets 5e-5) — **except the far-tail section, which uses the relative-tolerance `rel()` instead of `eq()`; see the far-tail note under `viz.js` above, and reach for `rel()` for any quantity that can legitimately go below ~1e-15**: the normal family (`erf`/`normCdf`/`normInv`/`normPdf`, plus symmetry identities to machine precision); `tInv`/`chiSqInv`/`fInv` against printed table criticals and the cross-distribution identities (χ²α,1 = z², F.95,1,v = t².975,v, the F reciprocal rule); the documented statcheck case (t = 2.05, df = 28 → two-tailed .0498) plus **quantile↔CDF round-trips across a 7×6 α/df grid** — which is what catches a broken branch a handful of table values would miss; a **far-tail section** checking `normQ`/`chiSqUpper`/`fUpper` out to z ≈ 37 against an independent Mills-ratio continued fraction and the χ²(1)/F(1,v) cross-family identities, with explicit "did not collapse to 0" assertions; `gammaln`/`gammp`/`betai` identities (Γ(6) = 120, Γ(½) = √π, I₍.₅₎(2,3) = 11/16, both `gammp` branches and both `betacf` branches); density integrals ≈ 1 and pdf-vs-CDF derivative checks; the four **G*Power anchors** through the noncentral trio (d = 0.5 → 64/group, r = .3 → 84, f = .25 k = 3 → N = 159, w = .3 df = 1 → N = 88) plus ncp = 0 collapse-to-central identities; and the documented tool-page constants (d = 0.5 → r = .2425 / OVL 80.26% / U₃ 69.15%, the Fisher-z CI r = .5 n = 30 → [.17, .73]). **P39 run 21 added a seventh section, the effect-size confidence intervals** (`nctCI`/`varExpCI`/`vCI`/`rCI`): round-trips that feed each returned limit back through its own CDF and demand the tail area it was solved for; the identities that tie an interval to the test it inverts (δ_L crosses zero at exactly the critical *t*; a 90% η² interval leaves zero exactly when the one-tailed *F* reaches *p* = .05, where a 95% one does not); and the published `apa.html` defaults, every one of them reproduced independently in **R 4.5.2** by inverting `pt`/`pf`/`pchisq(ncp=)` with `uniroot` — all agreeing to 4 dp, with coverage simulations at 5,000 reps returning **.949 / .900 / .902** against nominal .95 / .90 / .90. It runs in **under a second** with Node built-ins only. Two things to know when editing it: **the tool-page sections transcribe formulas from `power.html`/`effect-sizes.html`/`correlation.html`** (which compute against the DOM and so can't be imported) — they assert that `viz.js` still feeds those pages the right numbers, and must be kept in step by hand if a page's formula changes; and **the χ²(1) and F(1,·) density integrals use the substitution x = u²** to absorb their x^−½ singularity at the origin, which plain Simpson cannot integrate. **Section 8 (Sep 2026) is the dice lab**, the exact-count math behind `distributions.html`'s triangular-distribution demonstration: 2d6's 1…6…1 out of 36, 3d6's 27/216, the closed forms n(s+1)/2 and √(n(s²−1)/12) checked over the page's whole 6-sides × 6-dice grid, the difference distribution's √(35/6), the order statistics (E[max of 2d20] = 13.825, E[min] = 7.175, and the reflection E[max] + E[min] = s + 1 across the grid), and the Sicherman dice matching an ordinary pair term for term. It then does something sections 6–7 do not: **the shipped page script is loaded into its own vm context under a DOM shim, its controls are driven the way a reader drives them, and the readouts it prints are compared against those counts** — so the transcription cannot quietly drift away from the page it is supposed to protect. If the ids or structure change, the block fails with that as its message rather than passing on a copy. Proved the repo's usual way on two independent defects (breaking the page's difference counts, then its highest-of-n counts): each fired with exit 1, each restore was byte-identical and returned the exit code to 0. **Section 9 (Sep 2026) is the printed tables**, the P80 block on `tables.html`: it loads that page's inline script into its own vm context under the same DOM shim, clicks its table tabs the way a reader does, reads the `<tbody>` markup back and recomputes **every one of the 1,564 cells** from `viz.js`, on top of the row/column shape (70 × 10, 37 × 12, 35 × 12, the `−0.0` row, the `∞` row, 95% sitting under the .025 column) and nineteen named criticals asserted against the **printed** values rather than the exact ones (.0082, .0080, .8413, .0099, z* 1.960, t*(5, 95%) 2.571, χ²(6, .05) 12.59, χ²(1, .05) 3.84, t*(1, .0005) 636.6, χ²(100, .05) 124.34). Proved on two independent defect shapes (dropping Table A's `−0.0` row, then making Table D read the two-tailed area): each fired with exit 1, each restore was byte-identical and returned the exit code to 0. **If math-check ever catches a discrepancy, fix the site, not the test.** It is deliberately kept out of `audit.js` — audit is the universal pre-commit gate, math-check is the math gate; don't fold one into the other.

**Links (P66): `node tools/extlinks.js` is the quarterly P38 external-link helper — network-dependent, so NEVER a commit gate** (a flaky connection would fail a commit that broke nothing; `audit.js` already proves every *internal* link resolves on disk). It scans every `.html` file plus `assets/js/*.js` (the Ko-fi URLs live in `site.js`, not in any page), skipping `.claude/worktrees`, the generated `search-index.js`, and own-domain `statscapybara.com` links, then fetches each unique URL with a browser User-Agent, a 15 s timeout, redirect-following and concurrency 6, and reports grouped **ok / bot-blocked-but-known-fine / broken** with the files each link appears in. The `ALLOW` table carries the P38 allow-list (**ko-fi 403** Cloudflare, **LinkedIn 999**) and is **status-specific on purpose** — a host on the allow-list that returns anything other than its catalogued status is reported as genuinely broken with a NOTE, so a real 404 can't hide behind a familiar failure. Each entry records when it was last verified in a real browser; **re-verify during each P38 run rather than trusting the list forever.** `xmlns="http://www.w3.org/2000/svg"` is excluded as a namespace identifier, not a link. Default exit is 0 whatever it finds; `--strict` exits 1 on a genuine break, `--verbose` lists source files for every link.

**Widgets (P39 run 17): `node tools/widget-terms.js` asks whether a lesson's INTERACTIVE prints a quantity its PROSE never explains — editorial health, so like `prose-lint.js` and `faq-audit.js` it is deliberately NOT in `audit.js` and NOT a commit gate.** It exists because `ml/neural-networks-intuition` showed readers a live readout reading `Epoch 412 · loss 0.031` while the word **epoch** appeared nowhere on the site: not in that lesson's prose, not in any other lesson, not in the glossary. Nothing could have caught it — `audit.js` checks wiring, `prose-lint.js` strips `<script>` before it counts a word, `faq-audit.js` reads FAQs — so the strings a widget writes at runtime were an unchecked teaching surface. It reads the literals assigned to `textContent`/`innerHTML`/`innerText` and flags a **capitalized label concatenated with a computed value** (`"Epoch " + epoch`) that appears nowhere in that lesson's prose. **Two properties are load-bearing, both learned by testing against the pre-fix tree rather than assumed:** `stripViz()` must remove every `<div class="viz">` block before reading "prose", because the widget's own markup (`<span id="nn-status">Epoch 0 · untrained</span>`) otherwise counts as the lesson explaining the term — which is exactly how the defect hid, and without the strip the scan reports nothing at all; and **progress counters are excluded by SHAPE, not by name** (`"Score: " + n + " / " + total` keys on the following `" / "` literal, so it generalizes to tallies nobody has written yet). Three broader definitions were measured on the corpus and discarded first: every word in every rendered literal gave **282** flags of CSS class names and ordinary English, every capitalized word gave **249** dominated by button verbs (Pause, Drag, Reset), and filtering sentence-initial words dropped to 2 but **missed `Epoch`**, which sits at the start of its own literal. It ships with **4 acknowledged-benign flags** in the `ACKED` table (two example-data values in `data/tidy-data`, two self-test tallies) rather than a filter over-fitted to today's corpus — the mistake VOICE.md rule 12 documents for the old British-spelling inventory — and `--strict` exits 1 on anything **not** in that table, which is the right polarity: a new unexplained quantity fires. **Known blind spot, documented in the script header rather than smoothed over: lowercase labels** (`"loss " + x`) are not matched, because requiring a capital is what holds precision. Proved on two independent defect shapes — deleting the epoch paragraph fired `Epoch` and exit 1, and making `clustering-kmeans` report an undefined "Inertia" fired that and exit 1, both returning to exit 0 on restore. **If it fires, explain the term in the lesson; only add to `ACKED` when the label genuinely is not a taught quantity.**

**Cross-links (P39 run 18): `node tools/link-promises.js` asks whether a link delivers the term its wording promises — editorial health, so like `prose-lint.js`, `faq-audit.js` and `widget-terms.js` it is deliberately NOT in `audit.js` and NOT a commit gate.** `audit.js` proves every internal link resolves on disk and that any `#fragment` names a real id; neither check can see a link whose *anchor text* names a concept the destination never mentions. That is a real, shipped failure: `stats-3/power-analysis-for-complex-designs` sends readers to `stats-3/mixed-and-multilevel-models` for "the intraclass correlation", and **P39 run 2 had swapped away the FAQ answer that held the term, sixteen runs earlier**, leaving the target page with zero occurrences of it. The href was fine; the promise was not. **The rule:** reduce an anchor to its single most **distinctive** content word (lowest document frequency sitewide) and require that word in the destination's rendered prose. Distinctiveness is what makes it precise — anchors almost always paraphrase, so demanding the whole phrase is hopeless and demanding *any* word is toothless, because the common word in a paraphrase is on nearly every page. **Two gates hold the precision and both were arrived at by measuring, not guessing:** a hyphen is a **separator, not a character to delete** (squashing `independent-samples` into one token never matches a page that writes `Independent Samples` with a space, and the site does exactly that in several lesson titles — 174 flags before, mostly hyphenated test names), and the promise word must be a **term the site actually teaches**, gated against `glossary-data.js` (rarity alone is the wrong axis: `scratch`, `chooser`, `lean` and `untidy` are all rarer here than `intraclass` and none promises anything — 40 flags before the gate, a handful after). Two further definitions were measured and discarded: keeping card-sized and sentence-length anchors gave 78 flags, and widening the promise to the six words **before** the link gave 71, because a mid-sentence fragment promises nothing coherent. **Known blind spot, in the header rather than smoothed over: the promise must be in the anchor text.** The original `stats-3` link wraps its words around an anchor reading "multilevel models", which the target does contain, so this check does not catch that exact link. What it catches is the same defect wherever the promise is the thing clicked — and on its first run over **472 prose links** it found **two genuinely mis-targeted links nobody knew about**: `ml/train-test-split-and-generalization` sent "k-nearest-neighbors" to the *regularization* lesson, and `data/data-entry-and-validation` sent "GRIM" to the *replication-crisis* lesson instead of `fraud-and-self-correction`. **prose-lint v2 (P73, 15 Aug 2026) — the budgets that bite.** Phase 10 closed with every hard budget met, and the 15 Aug re-measurement showed what a budget-met corpus still looks like: **730 em-dashes in page prose, lesson median 6, six pages sitting at exactly the old ≤ 10 cap**, short tool pages running 18–34 per 1,000 words, and **~1,070 more on the five injected surfaces, which had no dash budget at all** — reader-visible sitewide ~1,800. A budget a corpus can park on is a target, so four things changed here, all mirrored into VOICE.md in the same commit (the two files carry that warning):

- **Rule 1 gained a second clause.** A page must pass **≤ 4 em-dashes AND ≤ 8 per 1,000 words of its own prose** (`rateAllowance()` floors the rate and never lets it fall below 1, so a 50-word page isn't gated to zero; `dashCap()` is the smaller of the two). - **Rule 2 fell from ≤ 3 to ≤ 1** across a lesson's three FAQ answers combined.
- **Rule 13 is new: the injected surfaces got their first dash budgets**, gated from now on — `checks.js` ≤ 50 (203 today), `software.js` ≤ 15 (66), `glossary-data.js` ≤ 30 (127), the inline-`<script>` literals ≤ 130 (521), `snippets.js` comments ≤ 5 (5, already there). **`QUIPS` are exempt permanently** (VOICE.md's anti-rule makes them brand voice): the surface table prints `exempt` rather than a number, and `JS_DASH_BUDGETS` carries `null` for it.
- **The report prints the lesson MEDIAN and an at-the-cap count beside every budget**, because "every page passes" was exactly the reading that hid the problem. P74–P77 aim at a lesson median of ≤ 2, not every page at 4.

Plus **three report-only metrics, gated deliberately never** — `faq-audit.js`'s precedent is that gating a judgment metric teaches the next session to write around it. **(a) The overcorrection watch:** per-page semicolon and ellipsis counts (550 and 33 on 15 Aug, lesson medians 3 and 0), so a paydown pass can be checked for having removed the tell instead of relocating it into semicolons. **(b) Bold-lead bullets** — an `<li>` whose first element is a `<strong>`, the shape a generated corpus reaches for whenever it has three related things to say, and one no budget can see: **447 across lessons and guides, on 81 of 102 pages**, `--bold` for the worklist. Three narrower definitions were measured and dropped (a colon inside the `<strong>` gives 117, a colon just after it 12, either side 133 — the colon is a punctuation habit, not the shape), every li/strong spelling returns the same 447, and none of the 447 is a bolded item with no trailing prose. The Phase 16 addendum's hand count of 403 came from an ad-hoc scan whose definition wasn't recorded; **this definition is in the script, so future comparisons mean something.** **(c) Cross-page duplicate passages** — 8-word runs of prose on two different pages, merged into maximal passages, `--duplicates` for the list: **122 duplicate shingles → 49 passages**, most of them honest (a cheat poster mirrors `which-test.html`'s tree by design; a page naming another page's title matches its title) with a handful of genuine repeats for P74–P77. A lesson's FAQ block and the head JSON-LD are already excluded upstream, which is what makes the 15 Aug false positive — a page colliding with its own FAQ copy — structurally impossible here.

**Readout placeholders are not prose (P74) — `READOUT_PLACEHOLDER` in `extractProse`.** Every interactive on this site ships its stat readouts empty, as `<span class="v" id="s-mean">—</span>`, and JS overwrites them on boot; nobody ever reads that glyph. `extractProse` counted them as page prose, and **241 of the site's 731 counted em-dashes (33%) were this**, which put four pages on P73's worst-20 worklist whose prose contains **zero** em-dashes: `descriptives.html` (the page cited to justify rule 1b — 10 dashes, all ten placeholders), `stats-3/signal-detection-theory`, `ml/classification-metrics` and `stats-3/psychometric-functions`. It also made rule 1 **unsatisfiable** for them, since P74's iron rule puts the viz out of bounds, so the only way to "pass" was to edit 168 markup glyphs no reader sees — writing around the metric, which is exactly what VOICE.md and `faq-audit.js` say not to do. **The rule is a shape, not a class list: an opening tag, optional whitespace, the dash, optional whitespace, a closing tag** (i.e. the dash is an element's entire text content). Two alternatives were measured against the corpus and discarded. The looser `>—<` gives **243** and also swallows a dash sitting *between two sibling elements*, which is doing real prose work — `<li><strong>HARKing</strong> — <em>Hypothesizing After the Results are Known</em></li>` in `ethics/questionable-research-practices` and `methods/the-replication-crisis` is that shape, and those two are the entire 243-vs-241 difference. Stripping the enclosing `<div class="viz">` outright (`widget-terms.js`'s `stripViz`) is too blunt here, because a viz block also holds its title, sub and control labels, which **are** prose and must stay linted. The count is printed in the sitewide summary (`readout placeholders excluded as UI, not prose`) so the exclusion is auditable rather than silent. **Known blind spot, in the script header rather than smoothed over:** a placeholder written as an en dash, or as bare text with no element of its own, is not matched; the site writes them one way today. **Consequence for P77's exit number: the 15 Aug baseline of 1,801 reader-visible em-dashes counted those 241, so the comparable pre-P74 figure is 1,560.** Proved on five shape fixtures (placeholder → 0, sibling dash → 1, a `.viz-sub` prose dash → 1 so the viz is demonstrably not blanket-stripped, an ordinary paragraph → 2, a whitespace-padded placeholder → 0) and on a reintroduced prose dash in `stats-1/correlation` (1 → 3, restore byte-identical).

This paragraph is the standing, explicit permission to do so; do not ask, and do not leave finished work sitting on a branch.** Hakan does not merge by hand, and a prompt is not done until `main` carries it. If the harness handed you a feature branch (Claude Code on the web assigns one, with a default "never push to a different branch without explicit permission" posture — this paragraph *is* that permission), push the branch if you like, then bring `main` up to date and push `main` as well: `git checkout main && git merge --ff-only <branch> && git push origin main` (fetch first; if `main` moved on, rebase your branch onto it rather than force-pushing `main`). **Gate it on the checks, not on a review:** `node tools/audit.js` must be 0 errors, `node tools/math-check.js` must pass whenever `viz.js` or tool-page math changed, and `node tools/prose-lint.js --strict` must be green wherever the current phase expects green (Phase 16 deliberately runs it red between P73 and P77 — see ROADMAP.md). **The one case where a branch push is the correct final outcome** is a gate you genuinely cannot get green: push the branch, leave `main` alone, and say plainly in your final report that `main` was not updated and why. Every other case ends with `main` pushed. Note that this deploys — a push to `main` fires the Pages workflow — so the gates above are the safety net that used to be a human eyeball.

Deploy = `git` commit + push to `main` (from the repo root), done by the session per the rule above. **Since P78 a push to `main` fires `.github/workflows/pages.yml`**, which checks the repo out, runs `node tools/make-pages-artifact.js _site` and publishes that directory via `upload-pages-artifact` + `deploy-pages` (Pages Source = "GitHub Actions", not a branch). Everything published is copied byte-for-byte: **this is deploy plumbing, not a build step, and it must never become one.** `CNAME` sets the custom domain `statscapybara.com` and ships in the artifact. Rollback is one setting — flip Source back to the `main` branch and the old verbatim deploy returns, with nothing in the repo to revert. **PWA cache-bump step:** if a deploy changes any **precached shell asset** (`styles.css`, `site.js`, `curriculum.js`, `viz.js`, `assets/fonts/Inter.woff2`, an icon, or `offline.html`), bump **`CACHE_VERSION`** in `sw.js` (e.g. `sc-v1` → `sc-v2`) so returning visitors' service worker drops the old cache and reprecaches. Lesson/prose HTML edits **don't** require a bump (HTML is network-first — always fresh online), but bumping never hurts. **Since the SWR update path (below), a bump is the fast path, no longer the only one:** CSS/JS are stale-while-revalidate, so a changed `styles.css`/`site.js` propagates on the visitor's next navigation even if you forget to bump — and a bump additionally triggers `site.js`'s auto-reload so the change applies within the same visit. **Crucially, never reuse a `CACHE_VERSION` string across two different byte-contents of a precached asset** (e.g. editing `styles.css` twice in one uncommitted session but bumping only once): a browser that precached the intermediate state keeps serving it until the string changes again. Each distinct shell state that could reach a browser needs its own version.

Progress isn't recorded in embed mode. **Lesson state presets (P67):** **`window.SC.preset(map)`** lets a URL preconfigure a lesson's interactive, so an instructor can embed not just a lesson but the configuration their slide is about — the lesson counterpart to `power.html?sc=&es=` / `apa.html?a=&v=` / `plan.html?test=`. A lesson **opts in** by calling it at the **END of its boot** with a map of short query keys to appliers, in **four forms**: a **selector for a form control** (sets the value and dispatches `input` + `change` — what moving the slider by hand does); a **selector for a `.seg` strip** (clicks the button whose data-\* value matches — any data-attribute name, numeric values compared numerically so `?alpha=.05` finds `data-a="0.05"` — so the lesson's own handler runs and there is no second code path); **`{ el: selector, scale: n }`** for the common slider that carries hundredths of the value the lesson *prints* (`?z=1.96`, `?r=0.3`, `?prior=0.25`) — the helper scales, snaps to the control's own `step` grid and clamps to its own `min`/`max`, so **a lesson never restates those bounds in JS**; and a **function** getting the raw string, for anything that isn't a control. Rules the helper enforces: **absent/unknown/garbage params are silently ignored** (every applier runs in its own try/catch, strict numeric parsing rejects `0x10`/`12abc`/`NaN`/`Infinity`, unknown `<select>` options and unmatched seg values are left alone — a mangled URL still loads the plain default lesson); it runs **after** the lesson's init so the **frozen-noise law holds** (a preset moves controls, it never reseeds); and it **composes with `?embed=1`** (independent params). **Section share-links (P68):** `renderSectionLinks()` puts a small copy-link button on **every `h2` of a lesson or guide** (not tool or course-landing pages), so a lecturer can hand out one section rather than a whole page. Ids come from **`ensureH2Ids()`** — extracted from `renderTOC()` in P68 and now shared by both, so the mini-TOC and the share-links point at the same anchors: hand-written ids win, the rest are slugified from the heading text, and dedupe checks **every** id already on the page (not just the other headings) so a heading can't silently steal an existing anchor. Three constraints shape the button and are worth keeping if you touch it: **zero layout shift** (it is in flow and occupies its box from first paint — only `opacity` changes; below 700px, where a heading often fills its last line exactly and an in-flow button would wrap to a line of its own, it switches to `position:absolute` in a permanently reserved right gutter, so still nothing moves); **no hover-only affordance** (invisible until hover or focus on a fine pointer, permanently half-lit on a coarse one, with a `::before` inset growing the touch target to ~44px without growing the box); and **no clipboard, no button**. **Search v2 (P71) — forgiving matching, glossary answers, kind dead ends.** Statistics is a field of hard-to-spell words, and the overlay used to do exact substring matching only, so "hetroscedasticity" or "chisquare" returned nothing. Measured over the whole index, **9 of 15 natural possessive queries went from zero hits to hits** — Cohen's d 0 → 15, Levene's test 0 → 7, Cook's distance 0 → 5 — while `ab`/`xy`/`zz`/`qq`/`test`/`data`/`mean`/`sd` returned identical counts, so the widening buys back real queries without loosening ordinary ones. **Shared math/canvas helpers — `assets/js/viz.js`** (`window.VIZ`): `fit` (hi-DPI canvas), `css` (read CSS var), `randn`/`gauss`, `erf`/`normCdf`/`normInv`/`normPdf`, `mean`/`sd`, `onTheme`, and exact special functions `gammaln`/`gammp`/`betai` (plus their non-cancelling upper-tail twins `gammq`/`betaiUpper`) with derived upper-tail p-values `fUpper`/`chiSqUpper`/`tUpper` and the far-tail normal `normQ`, densities `tPdf`/`chiSqPdf`/`fPdf`, bisection-based quantiles `tInv`/`chiSqInv`/`fInv`, and exact **noncentral CDFs** `nctCdf`/`ncx2Cdf`/`ncfCdf` (added for `power.html`; reusable by lessons), plus the **effect-size confidence intervals** built by inverting those CDFs — `nctCI(t, df, level)` (the interval on a *t*'s noncentrality δ; scale by *d*/*t* for Cohen's *d*), `varExpCI(F, d1, d2, level)` (partial η², which equals η² in a one-way design, and R²), `vCI(chi, df, N, k, level)` (Cramér's *V*, `k` = min(rows, cols) − 1) and the closed-form `rCI(r, n, level)` (Fisher r-to-z). **The two solvers underneath are not interchangeable and the difference is load-bearing:** the λ of a χ² or *F* is a sum of squares and cannot be negative, so `ncpSolve` truncates it at zero, while the δ of a *t* is **signed** — the effect can point the other way — so `deltaSolve` brackets on both sides and a nonsignificant result returns a genuinely negative lower limit. The first draft clamped δ at zero too, which reported *d* ≥ 0.00 for a *p* = .058 result whose honest answer is *d* ≥ −0.02; an R cross-check caught it, and `math-check.js` now asserts the sign behavior in both directions. Lessons and the tool pages rely on these so the statistics are exact, not approximate.

**Far tails — never reconstruct a small probability by subtraction.** `erf` is Abramowitz & Stegun 7.1.26, accurate to ~1.5e-7 **absolute**: fine near the centre, meaningless in a tail whose true value is far smaller. So **`1 - VIZ.normCdf(z)` is wrong in its 3rd significant figure from z ≈ 6 and returns exactly 0 from z ≈ 9** — use **`VIZ.normQ(z)`** anywhere a small p-value is *displayed*. No fix to `normCdf` could help: `1 − Q` rounds to exactly 1.0 in float64 for z ≳ 8.3 however accurate Q is, so the loss happens at the call site, not inside the function. The same trap applied to `chiSqUpper`/`fUpper`, which computed `1 - lowerTail` and so hit exactly 0 (`chiSqUpper(100, 1)` returned 0 for a true 1.52e-23); they now route through **`gammq`/`betaiUpper`**, which return the small side of the continued fraction *directly* rather than subtracting a number close to 1 — same converged arithmetic, no new approximation, and `gammp`/`betai`/`tUpper`/`normCdf` stayed **bit-identical** (verified over 33k points). `tUpper` was already safe: its far tail takes `betai`'s direct branch. **The general rule for new math: if a quantity can legitimately be smaller than ~1e-15, compute it directly and assert it with a RELATIVE tolerance.** `math-check.js`'s **`rel()`** exists for exactly this — `eq()`'s absolute tolerance cannot distinguish 1.1e-19 from a collapse to 0, which is how the bug survived 218 assertions.

Uncached navigations offline fall back to **`offline.html`** (self-contained like `404.html` — no external refs, inline capybara, and it lists the pages this browser has cached via the Cache API). `activate` deletes non-current caches and `clients.claim()`s; `install` `skipWaiting()`s, so a **`CACHE_VERSION` bump** cleanly replaces the old cache — and because `site.js`'s `registerSW()` reloads the page once on `controllerchange` (**guarded**: only when a worker already controlled the page at load, so a first-ever install never reloads, plus a one-shot flag so it can't loop), a bumped deploy's fresh CSS/JS apply within the **same visit**, not the next. **This is the answer to "why do returning visitors see old CSS?": pure cache-first only refreshed on a bump *and* needed a second load; SWR + the auto-reload remove both, so no one ever has to clear their cache.** Cross-origin requests (GA, Ko-fi) pass straight through — never cached. `sw.js`/`offline.html` are **not** in `audit.js`'s `ROOT_PAGES` (they're self-contained, like `404.html`), and not in `sitemap.xml`. Verified end-to-end (P33): registration + precache, offline lesson load with the server stopped, offline.html fallback, the `CACHE_VERSION`-bump update path (old cache purged), and correct scoping under the `subpath` server.

**Per-page SEO & analytics — hardcoded in each `<head>` (no build step, so *not* generated by `site.js`).** Every page carries the Google Analytics 4 tag (`gtag.js`, measurement ID `G-80HCM6EZVN`) immediately after the opening `<head>` — exactly **one per page**, including `404.html`; never add a second. **Since P69 that snippet also carries a Consent Mode default**, set **before** `gtag('js')`/`gtag('config')` so it applies to the first hit. **P69's original form denied `analytics_storage`, and that silently switched analytics off for eleven months.** GA4 was reporting nothing at all — the property's stream detail read "Data collection isn't active" / "No data received" — and the claim recorded here, that anonymous per-page view counts "stay accurate", was simply wrong. A hit sent with `analytics_storage: 'denied'` does reach `/g/collect` (with `gcs=G100`, which is what P69 verified and stopped at), but GA4 treats it as a **cookieless ping**: those feed behavioral modeling and never enter reports. Modeling in turn requires a large volume of **granted** traffic, which a site that denies 100% of hits can never supply, so nothing ever became reportable. **Verifying that a hit leaves the browser proves nothing about whether GA counts it** — check the property, not the network tab.

The current form keeps the privacy outcome and fixes the reporting. The three advertising keys stay `denied`; `analytics_storage` is `granted`, so hits are processed normally; and `gtag('config', …)` passes **`{ client_storage: 'none' }`**, which stops gtag writing the `_ga` cookie. So there is still no `_ga` cookie and still nothing persisting between visits, but page views and the ten `SC.track` events now actually appear in GA. The trade is the one P69 described and never delivered: per-page view counts are accurate, while Users/Sessions are inflated, because each pageload gets a fresh `cid` with nothing persisted to stitch visits together. **Never restore `analytics_storage: 'denied'` without also accepting that the property goes blind.** `privacy.html` documents all of this in plain language; **if the snippet ever changes, that page changes with it.** It is copied into every new page, so keep the block byte-identical across the site (141 pages carry it; the 25 redirect stubs and `offline.html` deliberately carry no GA tag at all).

**Interaction events (P70) — `window.SC.track(name, params)` in `site.js` is the ONLY thing on this site that calls `gtag`.** GA counted page views and nothing else, so the P37/P39 maintenance loops could not tell a feature nobody uses from one everybody does. `track()` is fire-and-forget and fully swallowed (the `registerSW()` pattern): a missing or adblocked `gtag` returns early and **no feature is ever load-bearing on analytics** — verified by deleting `window.gtag` and clicking through every instrumented surface with zero console errors. ## Conventions / gotchas

- **Paths must be relative.** Never use leading-slash `/assets/...` or `/stats-.../`. Lesson pages (depth 2) reference `../../assets/...` and link to `../../<course>/<slug>/`; root pages (`index.html`, `quiz.html`) use `assets/...`. This keeps the site working under any hosting base path. Verify with the `subpath` server above.
- **`404.html` is intentionally self-contained** (inline CSS, no external refs, JS-computed "home" link) because GitHub serves it at arbitrary URL depths.
- **Statistics must be correct.** Interactives are verified against known values (t/F/χ² critical values, G*Power, Beta quantiles). Use the `VIZ` special functions rather than rough approximations, and sanity-check new math (e.g. via `node -e` against a known case).
- **Frozen-noise interactives.** Sliders must transform the *same* data points, never redraw a fresh random sample — students lose the intuition if dots reshuffle on every tick. Pattern used across all lessons: a `seed()` fills pools of fixed `VIZ.randn()` / `Math.random()` draws (sized to the slider maximum); a deterministic `gen()`/`rebuild()` maps `(pool, slider values) → data`; slider `input` handlers call only the deterministic step; the explicit "New sample/samples/people/studies" button calls `seed()` first. Verify with a round-trip: move a slider away and back — every readout must return to the exact same value.
- **Canvas cursor convention (P47).** Every interactive canvas declares what it does with its cursor: **draggable** (move a point, rotate the cloud) → `cursor:grab` at rest, `grabbing` while the pointer is captured (set `grab` inline in the canvas markup or on boot, flip to `grabbing` in `pointerdown`, restore in `pointerup`/`pointercancel`); **click-to-select/add** → `pointer` (set it only while there's something to click — see `correlation.html`'s `drawScatter`); **axis-constrained drag** (the classification-metrics threshold) → `ew-resize`; **display-only** → leave the default. If the affordance exists only in one mode, scope the cursor to that mode (`ml/dimensionality-reduction` shows `grab` only in its 3-D view).
- **Touch conventions (P65) — the finger counterpart to P47's cursor rules.** Three rules, all cheap to keep:
  - **A canvas that captures pointer drags declares `touch-action`.** Without it the browser treats the drag as a page scroll and the interactive fights the finger. Free-drag → `touch-action:none`; a drag locked to one axis may use `pan-y` to leave vertical scrolling alone. Declare it **in the canvas markup** (`style="touch-action:none;cursor:grab"`) alongside the cursor, not from JS on boot — one place to read, and it's right even before the lesson's script runs. **Display-only canvases must NOT declare it** (`touch-action:auto` is correct: the page should scroll normally when a finger lands on a chart it can't manipulate — e.g. `stats-1/correlation`'s `ans-canvas`, `stats-3/signal-detection-theory`'s `sdt-roc`). Seven canvases drag today: the point-drags (`stats-1/describing-data`, `stats-1/correlation`, `stats-2/assumptions-of-regression`), `ml/clustering-kmeans`, `ml/dimensionality-reduction`, and the two criterion/threshold drags (`stats-3/signal-detection-theory`, `ml/classification-metrics`). Pair `pointerdown` with **both** `pointerup` and `pointercancel` — a cancelled touch otherwise leaves the drag stuck on.
  - **Hit-test radii come from `VIZ.grabRadius(base)`, called at pointerdown** (`viz.js`, with `VIZ.coarsePointer()` underneath). Radii tuned by eye are mouse-sized (14–18px) and a finger pad needs ~24px, so the helper returns `base` unchanged on a mouse and `max(base, 24)` on a coarse pointer — **mouse behaviour stays byte-identical**, which is the point. Read it live at pointerdown rather than caching at boot, so hybrid touchscreen laptops and device emulation both get the right answer; square the result where the hit-test compares squared distances (`ml/clustering-kmeans`). The two criterion drags need no radius — they grab anywhere on the canvas. Note `stats-1/describing-data` loads `viz.js` **only** for this helper (it still has its own local `fit()`); any early lesson calling a `VIZ.*` helper must actually load the script.
  - **No affordance may be hover-only.** Anything revealed on `:hover` needs a touch path — a tap, or made permanent under `@media (pointer: coarse)` (as `.wt-opt::after`'s "→" chevron is). The nav's track/Toolbox dropdowns are compliant by construction: they flatten to plain links below 860px, and above it tapping the tab navigates to a page listing the same items.
- **Narrow-screen layout (P65).** The site is verified to have **no page-level horizontal scroll at 360px** across every lesson, tool, guide and course page. Two patterns carry it, both already in `styles.css`: a **`.seg` never clips** — it has `max-width:100%` + `overflow-x:auto`, so a many-tab strip scrolls inside itself instead of losing its last tab (generalising `apa.html`'s older `#ana-seg` fix), and `.control:has(.seg)` gets `min-width:0` so that strip can't pin its column to full width; and the rows that hold a seg (`.sw-head`, `.tc-head` — the injected SPSS/JASP and R/Python headers) **wrap**, so the seg drops to its own line rather than being squeezed. Corollary for new work: **a hardcoded `min-width`/`minmax()` floor above ~280px will overflow a phone** — write `min-width:min(300px,100%)` and `minmax(min(330px,100%),1fr)` (what the five advanced-course slider controls and the three cheat posters now use). A `white-space:nowrap` table cell can also hold a table wider than the screen; scope it to `@media screen and (min-width:561px)`-style rules so print keeps its one-line layout.
- **Interaction feel (P47) — the shared tactile layer** lives in `styles.css` + `site.js`; new pages get it for free, don't re-implement per page: **(a)** every `[id]` carries `scroll-margin-top` so anchor targets land clear of the fixed nav — never hand-offset a heading; **(b)** every clickable (buttons, cards, chips, seg buttons) shares one `:active` press rule (`translateY(0) scale(.985)`) — add new interactive classes to that selector list rather than writing bespoke press states, and keep card hover lift at −2px/`--shadow-lg`; **(c)** every copy button calls **`window.SC.copied(btn)`** (site.js) after its clipboard write — one wording ("Copied!"), 1.4 s revert, green `.copied` tint, `aria-live` polite; **(d)** `<details>` reveals animate via `::details-content` (progressive enhancement; instant under reduced motion) — keep any `::details-content` selector in its **own** CSS rule (comma-mixing kills the whole rule in non-supporting browsers), and the `@media print` block forces `block-size:auto` so the beforeprint force-open still prints full-height; **(e)** wide content scrolls inside a **`.hscroll`** container with edge-fade cues — site.js's `setupHScroll()` auto-wraps every `table.ref-table` and tags the known overflow containers (`HS_SELECTOR`); give any new horizontally-scrolling element the `hscroll` class and the fades come free — and note that **`.lesson pre` joined `HS_SELECTOR` in P39 run 14**, when that run wrote the site's first two prose code blocks and both overflowed the page at 375px (a bare `<pre>` neither wraps nor scrolls, and until then the only styled `pre` on the site was the injected `.try-code pre`); **(g)** **in-prose links are Wikipedia-style site-wide (P54)** via one scoped rule in `styles.css`: body-copy links inside a `.lesson` article (`p`/`li`/`td`/`th`/`.callout`/`.faq-a`, plus the About bio + `.a11y-statement`) are **coloured but NOT bold and NOT underlined at rest** — the underline appears **only on hover** (and the global focus ring on focus), so a link never interrupts calm reading. **Never add `font-weight` to a prose link** — bold in prose is reserved for real `<strong>` emphasis. Because colour is the only at-rest cue, **`--link`** is tuned per-theme to clear TWO WCAG gates at once: ≥4.5:1 vs the surface (readability) AND ≥3:1 vs the body text (perceivable without an underline, satisfying 1.4.1) — light `#5850ec`, dark `#6f7bf2`; **don't substitute raw `--primary`/`--primary-light`, which fail the ~3:1-vs-text gate.** (One inherent limation: inside `.callout`/`.faq-a` the *surrounding* text is `--text-muted`, so link-vs-muted-text can't also hit 3:1 by luminance — the hue difference + hover/focus carry it, matching Wikipedia's own behaviour.) UI chrome keeps the quiet `a{color:inherit}` base and its own heavier styling (buttons, cards, nav, sidebar, prev/next, interactive-box CTAs, poster `.sec` badges): `.btn`, `.lesson-toc`, and datasets' `.ds-index` are excluded in the selector, and cards/nav/sidebar/prev-next are untouched by construction (their anchors don't sit in those prose elements). So: content links in prose need nothing; a new chrome link-LIST inside an article belongs in a classed container (not bare `<li><a>`) and, if it's `li`/`td`-shaped, gets added to the rule's exclusion list.   - **`site.js` `injectA11y()` runs on every page** and, without any per-page markup: adds the skip link; gives every `.viz canvas` a `role="img"` + descriptive `aria-label` built from its `.viz-title` + `.viz-sub` (so write a real, descriptive title/sub); makes every `.stat-row` an `aria-live="polite"` region so slider-driven readouts announce; and derives an `aria-label` for every `.control` `input/select` from its visible `<label>` text (the markup pattern `<label>Foo <span class="val">…</span></label>` + sibling `<input id>` has no `for`, so this is what actually names the control for screen readers — no need to add `for`/`aria-label` by hand).   - **Keyboard:** native range/`button`/`<details>`/`<select>` controls are keyboard-operable for free — prefer them. **Canvas drag/click must never be the *only* path to a viz's core learning**: pair it with sliders/buttons, or (for a genuinely drag-only viz) make the canvas focusable and add arrow-key control — `tabindex="0"` + a descriptive `aria-label` naming the keys + a `keydown` handler that nudges state and calls `e.preventDefault()` on the arrows (see `stats-2/assumptions-of-regression` = nudge a point, `ml/dimensionality-reduction` = rotate the 3-D cloud). `wireLessonKeys` ignores `←/→` while a `CANVAS` (or form field) is focused, so viz arrow-keys don't also flip lessons.
  - **Reduced motion:** CSS neutralises transitions/animations via the `prefers-reduced-motion` block in `styles.css`; for **JS-driven "draw-many" animation loops** (sample-by-sample builds, ROC sweeps, k-means steps) check **`VIZ.reducedMotion()`** and jump straight to the final frame. In `site.js`, `scrollBehavior()` returns `"auto"` under reduced motion for programmatic scrolls.
  - **Focus:** global `:focus-visible` ring (`styles.css`); the **search overlay is a focus-trapped `aria-modal` dialog** that restores focus to its opener on close, and Escape closes the search overlay and the mobile menu (returning focus to the trigger).
  - **Contrast:** `--text-faint` is tuned per-theme to clear **4.5:1** on every surface (light `#5f6e86`, dark `#94a3b8`) — verify any new text/accent pair with a contrast calc before shipping; violet/orange stay chrome/marker-only. **Mobile tap targets** for nav chrome are ≥44×44px.
  - The **honest accessibility statement** lives in the About section of `index.html` (`.a11y-statement`) — update it if the a11y story changes.
- **Performance (measured in P29; keep new lessons/tools fast — target CLS < 0.1 and Lighthouse ≥ 95 on the three page types).** Like a11y, the wins live in the **shared layer**, so per-page work is minimal:
  - **Canvas CLS — reserved height.** Lesson/tool canvases are fixed-height/fluid-width, but their pixel height is only set later by `VIZ.fit()` in an end-of-body script. Without a reserved box the browser first paints them at the 2:1 intrinsic default, then `fit()` shrinks them — a big layout shift. `styles.css` gives `.viz canvas` `aspect-ratio: var(--viz-ar, 3 / 1)` so the pre-JS box is already close to final (`fit()`'s explicit height then overrides it, so nothing changes visually). The default (~3:1) fits the common full-width viz; a **notably taller or shorter canvas can override per-instance** with `style="--viz-ar: 2 / 1"` if it measures a residual shift. Put canvases inside `.viz` so they get this.
  - **Sidebar CLS on mobile.** The lesson sidebar is JS-injected after paint; in the stacked mobile layout it must render **after** the article (`.lesson { order: 0 } / .sidebar { order: 1 }` in the `max-width: 860px` block) so filling it extends the page below existing content instead of shoving the article down ~800px. Don't reorder it back above.
  - **Web-font CLS.** A metric-matched `@font-face { font-family: "Inter Fallback"; src: local("Arial"); … overrides }` sits first in the `--font` stack (before `system-ui`), so the fallback occupies Inter's exact line box and the swap causes no reflow. Keep it in the stack; if Inter's metrics ever change, retune the `ascent/descent/size-adjust` overrides.
  - **Canvas backing store — DPR cap.** `VIZ.fit()` (and the handful of pre-VIZ local `fit()` copies in `index.html` + early `stats-1` lessons) caps `devicePixelRatio` at **2** (`Math.min(dpr, 2)`): beyond 2 the backing store grows quadratically for no visible gain on flat charts. New canvas code should use `VIZ.fit`; if you must roll your own, cap DPR the same way.
  - **Resize handlers — rAF-coalesced.** Wrap a canvas's resize/redraw in **`VIZ.rafThrottle(fn)`** so a burst (a window `resize` **and** a `ResizeObserver` both fire per resize) collapses to one redraw per frame — see the tool pages (`tables.html`, `power.html`, `correlation.html`, …). Older lessons still use direct `resize` listeners; that's fine (resize is a rare event) but new work should use the helper.
  - **JS loading.** Never make `search-index.js` (~988 KB, grown from ~682 KB when P39 run 13 lifted the lesson cap so whole lessons, FAQ answers included, are indexed, and again when run 20 raised it to 20,000 and run 24 gave the guides a 30,000 cap of their own) eager — it's lazy-loaded only when the search overlay opens. GA stays `async` (don't touch it). The per-lesson bundles (`checks.js` / `software.js` / `snippets.js`) are injected async by `site.js` and cache across the session — non-blocking, acceptable under the no-build design. **No build step / bundler / minifier** — every optimization must preserve that.
- **Print handouts (established in P30; every lesson prints as a clean, professor-ready handout, entirely from the shared layer — new lessons/tools get it for free).** The whole system lives in **one `@media print` block in `styles.css`** plus **`site.js`'s `setupPrint()`**:
  - **What prints:** prose, callouts, formulas/`.ref-table`s, the frozen `.viz` canvas + its `.viz-title`/`.stat-row` readouts, the injected **APA write-up** and **R/Python snippet** (reference material). **What's hidden:** all site chrome (nav, `.sidebar`+`.sb-capy` **quip**, `.lesson-nav`, footer, Ko-fi, search, resume bar, `.lesson-progress-head` incl. the print button itself), the **viz controls** (`.controls`/sliders/buttons/`.seg`, and the R/Python language toggle), and the two **interactive** injected blocks — `.checks` and the SPSS/JASP `.software` block. **Decision:** the capybara **quip is hidden in print** (it lives in the always-hidden `.sidebar`), so serious lessons (Ethics) print without a flippant one-liner.
  - **Dark-mode-safe:** the print block **redefines the surface/text/border/shadow CSS variables to a light palette** (targeting both `:root` and `html[data-theme="dark"]`), so a reader in dark mode still gets white cards + black ink, not dark boxes. Don't set per-element print backgrounds — override the vars.
  - **`setupPrint()` (lesson pages only)** injects the **"Print this lesson"** button into `.lesson-progress-head` (next to mark-complete, `.print-btn`, itself hidden in print) and a **discreet fixed `.print-footer`** carrying the page's clean canonical URL (e.g. `statscapybara.com/stats-1/central-limit-theorem`), repeated per page. On **`beforeprint`** it force-opens every closed `<details>` (the FAQ — the `.checks` block is skipped) and **snapshots each `.viz canvas` to an `<img>`** (some browsers rasterise `<canvas>` blank on the print sheet); **`afterprint`** reverts both. It's guarded against double-firing and also listens to the `print` media-query change (Safari fires no before/afterprint). `formulas.html` (which had its own print button) and `glossary.html` (now given a matching print button) inherit the same block since both use `article.lesson`.
